# M3-01 模拟面试模块设计与实施规划

**状态：待评审；仅设计，不代表 M3 已实现。** 依据现有代码、`docs/architecture/DECISIONS.md`、`docs/reference/prototype-v0.4.html` 和 M2 验收报告整理。本文的 API、表和状态均为建议草案；标注“待决”的产品规则在确认前不应固化为默认行为。

## 1. 目标、范围与现有依据

M3 计划提供文字模拟面试：选择标准题库或预设岗位，可输入 JD；选择练习或正式模式、限制方式；依次回答主问题和动态追问；结束后查看完整或部分复盘。已完成与未完成记录必须分开展示。未完成面试仅复盘有效回答，不生成综合分数或默认学习任务，且不能继续作答。正式模式结束前不得展示评分和评价；练习模式允许逐题反馈。

V0.4 原型还展示 Python 后端、AI 应用两个题库和相应岗位、岗位模式可选 JD、练习可跳题、按主问题数量或时长二选一，以及未完成场次不能续答。原型的 2/3/4 题、5/10/15 分钟、关键词匹配、固定追问和演示分数只是原型示例，不作为已确认的生产取值或评估算法。语音和简历个性化在原型中属于后续范围；本设计不加入。

## 2. 架构与复用

沿用 React + TypeScript、FastAPI、Pydantic、SQLAlchemy AsyncSession、PostgreSQL、Alembic 和 OpenAI 兼容接口；不新增服务或大型框架。建议新增 `api/v1/interviews.py`、`models/interview.py`、`schemas/interview.py`、`services/interview*.py` 和前端 `features/interviews/`、面试页面；名称为建议，不修改既有表与 API。

| 现有能力 | 复用方式 | 必须独立实现或调整 |
| --- | --- | --- |
| `app/llm/client.py` 的服务端密钥、HTTPX 流式请求和 `ModelError` 分类 | 抽出通用模型调用能力，保留 M2 接口与错误脱敏 | 面试专用提示、结构化结果解析与校验、失败处理和上下文预算；现有 `stream_chat` 只产生文本，不保证 JSON 或确定性 |
| `api/v1/chat.py` 的 SSE `start/delta/done/error`、断线清理思路 | 复用事件格式和取消资源清理经验，复用前端流读取基础代码时先抽取并回归 M2 | 面试题目、回答、状态及报告必须由面试服务决定；普通 `Conversation`/`Message` 不是面试状态机。当前 chat 的部分内容仅结束时持久化，进程硬崩溃可能丢分片 |
| `db/session.py` 的请求级 AsyncSession、事务与 Alembic | 复用数据库连接、依赖注入及迁移框架 | 面试表、行级并发控制、幂等操作、到期/中断恢复独立实现；模型网络调用不得持有长事务 |
| `services/chat.py` 的 PostgreSQL advisory lock 和恢复经验 | 可抽取带命名空间的通用锁工具，或针对面试单独实现 | 不能直接调用其 `recover`：它会把聊天 `streaming` 消息标为 `cancelled`；面试终止语义不同。确保与聊天锁 key 命名空间隔离、异常时释放或失效连接 |
| 现有 React Router、TanStack Query、布局及 Markdown 渲染 | 扩展 `/interviews/new`、面试进行页、记录和报告页；复用现有样式和可访问性模式 | 实现面试专用状态、反馈可见性、计时与异常提示；不要依赖前端隐藏来保护正式模式反馈 |

`services/chat.py` 的 24000 字符历史限制只是一种近似，且不应直接拼接跨业务聊天历史。面试上下文由服务端按场次和当前问题构建，包含有限 JD、相关题目和有效回答；字符上限及模型 token 适配待评审。用户答案、JD 和模型输出均是不可信文本；校验长度并分隔数据与指令，避免在日志中记录密钥或完整敏感输入。

## 3. 面试状态机

服务端是唯一权威。每个面试从创建后的 `pending` 开始，`completed`、`terminated`、`interrupted` 均为终态；终态不可继续作答，也不可重新开始同一场次。需要再次面试时创建新场次。`report_status` 与面试状态分离，报告生成失败不能反向改变面试终态。

| 当前状态 | 事件 / 条件 | 目标状态 | 原子副作用及约束 |
| --- | --- | --- | --- |
| `pending` | 用户开始，配置有效、首题可用 | `in_progress` | 写入开始时间、服务端期限及当前题；重复开始必须幂等，不能重新计时或重复出题 |
| `pending` | 用户未开始或开始前放弃 | 待决 | 是否允许取消、是否进入历史列表待产品确认；不得伪造已完成面试 |
| `in_progress` | 按确认的完成判定规则达到限制、正常收尾 | `completed` | 锁内冻结回答和终止时间，只有符合有效作答门槛的场次可生成完整报告；门槛待决 |
| `in_progress` | 用户明确提前结束 | `terminated` | 锁内冻结已提交有效回答，记录原因与终止时间；不得继续作答或生成综合分数 |
| `in_progress` | 已确认的异常中断事件 | `interrupted` | 锁内冻结已提交有效回答，记录原因；不得续答或生成综合分数。触发条件待决，见第 9 节 |
| 任一终态 | 重复结束、过期提交或开始 | 保持原状态 | 已处理的同一幂等请求返回原结果；其他非法变更返回 409，不产生题目、回答或报告重复记录 |

**时间限制：**开始事务记录数据库时间 `started_at` 和不可由客户端修改的 `deadline_at`。客户端倒计时仅展示；提交、出题、结束和读取/恢复时，服务端在同一锁内检查数据库时间。到期应原子冻结场次并拒绝过期作答；到期后属于 `completed` 还是未完成，以及到期瞬间已提交但尚未确认的回答如何判定，待产品确认。在确认前不把原型的“时间到即未完成”直接当成正式规则。无独立定时服务时采用请求触发的惰性到期检查；如果要求无人访问也准时终态化，需要另行确认调度方案，不能宣称惰性检查会主动运行。

**主问题数量：**`main_index` 只在主问题被正式创建时增加，追问不占主问题配额；已提交的追问有独立深度。达到配置的主问题上限后，是否允许完成当前主问题的追问、跳题是否计数、题库不足时如何结束均待决。每次转换都在服务端校验计数与追问深度上限，不能信任客户端传入的题号或深度。

**异常与不续答：**建议面试与生成任务分离：模型短暂错误先保留已提交回答并明确显示失败，是否允许在原场次重试生成由待决规则决定；一旦场次被判定为 `interrupted` 就不能恢复作答。不能把客户端单次断流直接等同于服务进程崩溃，也不能仅依据单次刷新就误判其他正常标签页；刷新、断网、失联时何时终止需明确产品规则。使用持久化操作状态、拥有者与到期租约，读取时在锁内判断过期任务；租约不是用户在线证明。

## 4. 配置、提问与评估

### 配置与出题

- 标准题库选择知识方向；岗位定向选择预设岗位并可填写 JD。预设岗位及题库的名称可参考 V0.4，正式题目内容、覆盖范围和人工审核流程待确认。题库应是真实维护的数据，不将 M1 学习文章或原型的演示问题当作已经完成的正式题库。
- 快照本次配置、题目文本和版本，保证题库更新后历史可复盘；JD 仅服务端保存并按需发送至配置的模型服务。语义提取、JD 与岗位冲突时优先级、题目抽样方式待决；可先采用审核过的规则方案，不能把原型关键词演示宣传为语义解析。
- 一个主问题下可有零到上限条追问；服务端基于该问题及已提交回答让模型给出候选，并校验结果属于允许的动作和格式。追问深度数值、是否每题都追问、追问失败时行为待决。无效或无法解析的输出不得伪装为真实追问；超时/断流不能自动丢弃已提交回答。
- 练习允许逐题反馈，原型允许跳题；跳题在数据库中明确记录，不计入有效回答。正式模式是否允许跳题、跳过后的数量规则待决。

### 报告与可见性

| 场次 | 可见反馈 | 报告约束 |
| --- | --- | --- |
| 练习中 | 已提交题目的逐题反馈可见；是否逐追问反馈待决 | 不因反馈生成正式学习任务或修改掌握状态 |
| 正式进行中 | 不返回评分、评价、参考答案及完整报告；服务端 API 和 SSE 均需过滤 | 只返回必要的题目、作答与进度，不以隐藏前端组件作为保护 |
| 正常完成 | 可生成完整报告及综合评分，具体维度、量表、评分方式和失败重试待决 | 报告必须以已保存的有效作答为依据；标明 AI 评价而非客观能力证明，不能生成虚构回答 |
| 提前终止 / 异常中断 | 仅实际有效作答的部分逐题复盘 | 服务端和数据库约束禁止综合分数、默认学习任务；无有效回答时返回“无可复盘内容”，不调用模型填充虚构内容 |

报告独立状态建议为 `not_requested` / `generating` / `ready` / `failed`；`GET` 对未生成或失败返回明确状态，而不是空报告冒充成功。生成使用可幂等重试的操作记录，快照输入并在保存时再次检查面试终态与报告类型。M3 不负责创建默认任务；未来推荐任务仍需用户确认。

## 5. 数据模型草案

新增迁移仅建表、索引与约束；不删除或改写 M1/M2 数据。所有关联字段及具体索引由实现阶段结合查询验证。下列为建议，不把评审未决规则写死为数据库默认值。

| 表 | 关键字段 | 关系与约束 |
| --- | --- | --- |
| `interview_presets` | `id`、`kind`（题库/岗位）、`name`、`version`、`active`、配置 | 可版本化维护的预设；不将 V0.4 演示数据当成正式种子 |
| `interview_question_bank` | `id`、`preset_id`、题目正文、知识点、版本、启用状态 | 预设可关联多个主问题；历史使用题目快照，避免编辑影响旧记录 |
| `interviews` | `id`、`status`、`mode`、预设/版本快照、`jd`、`limit_type`、数量/时长、`started_at`、`deadline_at`、`ended_at`、`end_reason`、`main_index`、`version`、时间戳 | 状态/模式/限制类型使用 CHECK；数量、时间使用正数约束；`version` 用于乐观并发或状态比较更新；不引用普通聊天会话 |
| `interview_questions` | `id`、`interview_id`、`main_number`、`parent_id`、`depth`、`kind`、`content`、来源/版本快照、创建时间 | 主问题及追问均持久化；自关联父问题须属于同一场次、层级合理；唯一约束防止重复序号 |
| `interview_answers` | `id`、`interview_id`、`question_id`、`content`、`kind`（回答/跳过）、`submitted_at`、`request_id` | 一个问题最多一次正式提交；`(interview_id, request_id)` 唯一；跳过与有效回答可区分，不能用空文本冒充有效答案 |
| `interview_operations` | `id`、`interview_id`、`kind`、`request_id`、输入摘要、`status`、租约拥有者/截止、结果引用、错误类别 | 记录出题/追问/反馈/报告操作；对同一场次和幂等键唯一，并拒绝同键不同请求体；网络调用在事务外，提交结果前重新核对状态和操作所有权 |
| `interview_reports` | `id`、`interview_id`、`type`（完整/部分）、`status`、结构化逐题反馈、可空综合分、版本、生成时间 | 单场各类型至多一个有效报告；部分报告 DB CHECK 综合分为空，服务层还要检查场次终态与有效回答；报告仅在校验后原子发布 |

数据库不能用跨表 CHECK 直接保证“只有已完成场次能有完整报告”；需在面试行锁内检查状态并写报告，可选触发器作为进一步约束，不能仅靠 ORM。反馈和评分结构先由 Pydantic 验证，明确题目/回答引用；约束和事务设计需以 PostgreSQL 集成测试验证。

## 6. API 草案

统一 `/api/v1/interviews`，所有写操作建议使用 `Idempotency-Key`（每个逻辑操作稳定且仅用于同一请求体）；资源不存在 404，状态/版本冲突 409，非法输入 422，模型失败提供脱敏错误。以下不表示当前接口已存在。

| 方法与路径 | 作用与关键约束 |
| --- | --- |
| `GET /interview-presets` | 返回可用岗位、题库及配置元数据；真实题库内容是否预览待决 |
| `POST /interviews` | 创建 `pending`，提交预设、可选 JD、模式及限制；服务端验证并保存配置快照；重复键返回同一场次 |
| `GET /interviews?status=completed|incomplete` | 分开查询完成与未完成记录；`incomplete` 映射 `terminated`/`interrupted`，`pending`/进行中如何展示待决 |
| `GET /interviews/{id}` | 返回状态、计时、进度和当前可见问题；正式模式进行中绝不返回评分/评价/参考答案 |
| `POST /interviews/{id}/start` | 在事务内 `pending → in_progress`，记录服务端时间并返回已提交的首题或明确生成状态；幂等重复不新建题目 |
| `POST /interviews/{id}/answers` | 携带 `question_id`、回答或允许的跳过动作、期望版本；锁内检查状态、截止、当前题、幂等键并提交；同题重复或旧版本冲突返回 409 |
| `GET /interviews/{id}/operations/{operation_id}` | 查询模型处理状态与合法可见结果；重连可读已落库内容，不能把 SSE 分片当成已完成题目 |
| `GET /interviews/{id}/operations/{operation_id}/events` | 可选 SSE 传递状态或生成文本；`start/delta/done/error`，`done` 仅在结果提交并验证后发出；断开不自动确认答案或完成面试 |
| `POST /interviews/{id}/finish` | 明确区分正常完成与主动终止；服务端验证完成条件，原子冻结状态；客户端不能自行声明已完成绕过条件 |
| `POST /interviews/{id}/report`、`GET /interviews/{id}/report` | 前者幂等申请生成/重试，后者返回生成状态和允许的报告；终态及报告类型双重校验，未完成严禁返回综合分或默认任务 |

题目生成可采用“提交答案 → 返回操作 ID → 查询或 SSE”的两阶段模式，避免长模型请求持有数据库事务；若取消连接不等于取消操作，应在接口中明示。正式模式对逐题反馈采用服务端生成时机或响应过滤双重约束，所有查询路径（包含事件流、详情和报告）都不得泄露。报告重试和用户结束并发时，以锁内最终状态为准。

## 7. 一致性、恢复与故障处理

1. 写入前对 `interviews` 使用 `SELECT ... FOR UPDATE` 或版本条件更新，并在同一事务内检查当前题、`status`、截止时间、配额和幂等键，先提交用户答案与操作记录；唯一约束兜底。并发相同请求返回同一结果，不同请求只有一个成功，迟到结果不得覆盖终态。
2. 模型调用前提交事务；用持久化 operation 的唯一 ID 和租约认领，模型返回后开启新事务重新验证状态、版本和租约，再原子保存候选题/反馈/报告与操作结果。外部模型调用无法保证恰好一次，崩溃重试可能产生多次模型请求或费用；只能保证本地落库至多一次，不能承诺供应商恰好执行一次。
3. 客户端超时或断流时用原幂等键查询结果，不能盲目重复创建答案；流传输和业务完成分别记录。进程崩溃后依赖租约过期及下次请求触发恢复；租约时长、心跳和异常中断定义需评审。到期的旧执行者不能在新租约或终态出现后写回。
4. 提前结束、时间到、并发答案及模型响应竞争时，以数据库锁和服务端时间确定顺序；冻结后拒绝新结果。模型错误分类复用 M2 脱敏信息；格式错误、超时和断连不产生虚构问题、分数或默认任务。对于模型生成失败是重试、结束还是中断，遵循评审结论而非静默推进。
5. 单实例无用户身份认证；隔离面试 ID 只保证业务范围一致性，不构成访问控制。保留本机绑定，公开使用前需访问保护。旧聊天数据、M1 阅读进度及原有接口均不被迁移修改。

## 8. M3-02 至 M3-06 任务拆分

每个模块完成并验证后单独使用中文规范提交；依赖评审结论的工作不得将待决项当成既定规则。

| 任务 | 修改范围 | 前置依赖 | 验收标准 |
| --- | --- | --- | --- |
| **M3-02 数据与状态机** | 面试 ORM、非破坏迁移、预设/题库数据结构、状态转换服务及数据库约束 | M3-01 评审；状态、时间到及有效回答规则确认 | 真实 PostgreSQL 迁移前后 M1/M2 数据一致；合法/非法状态、时间边界、终态禁止续答、主问题计数与跳题规则有测试；不引入虚构正式题库 |
| **M3-03 会话与回答 API** | 配置、创建、开始、列表、详情、回答和结束 API，幂等与并发事务 | M3-02；配置范围、题库来源、限制取值确认 | 重复键、同题并发、开始/结束竞态、过期与版本冲突在双进程 PostgreSQL 测试通过；正式模式所有查询均不泄露评分评价；不影响 M1/M2 API |

## 9. 待产品评审确认

1. **到期与完成判定**：时长到、达到主问题数、题库提前耗尽分别属于正常完成还是未完成？至少多少有效回答才允许完整报告？到期前已发出但服务器到期后收到的回答如何处理？
2. **限制取值**：按题数和按时长是否互斥？允许的上下限、默认值、最大追问深度为何？追问是否受剩余时间限制？跳题是否占主问题数？
3. **中断边界**：刷新、标签页关闭、主动离开、浏览器网络断线、服务器重启、模型失败分别何时判为 `interrupted`？是否有宽限期？一旦判为未完成不可续答的规则保持不变。
4. **题库与 JD**：正式预设岗位、题库及题目由谁提供和审核？JD 是否仅岗位模式可用、长度/保留期为何、是否要求语义解析及冲突处理？没有可用题目时如何提示？
5. **追问与反馈**：何时追问、允许的最大深度、追问失败时可否重试或跳过？练习模式的跳题与逐题反馈是否包含追问？正式模式是否允许跳题？
6. **评分与报告**：综合分量表、维度、权重、证据引用和报告结构如何定义？有效回答如何判断？部分复盘是否允许 AI 对单题给出分数，还是只能文字反馈？报告生成失败的重试与终止策略是什么？
7. **操作与数据**：`pending` 可否取消及其历史归类？同一用户是否允许多场同时进行？删除、导出、数据保留期和隐私提示是否属于 M3？是否需要用户显式同意将 JD 与回答发送给模型服务？

## 10. 风险与验证边界

- 未确认的时间到/中断定义会直接影响终态和评分资格，是开始实现前的产品阻塞项；不可用原型演示数据代替决策。
- 数据库事务无法覆盖外部模型请求；进程失联可能增加模型调用费用。租约、幂等和终态校验保证本地一致性，但需要真实 PostgreSQL、双进程及故障注入验证。
- 模型结构化输出、提示注入、长 JD、上下文上限和评分稳定性均需验证；生成失败应如实展示，不得以固定模板假冒模型评价。
- 正式模式提前暴露评价、未完成产生综合分或任务属于阻塞验收的产品错误；在 API、数据库写入和 UI 三层测试。
- 本报告仅为设计，无 M3 实现、迁移或新依赖；待评审确认后再进入 M3-02。
