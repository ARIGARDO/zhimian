# M3-02 面试数据模型与状态机报告

> 本报告记录 M3-02 当时的实现与测试；规则以 M3-02-Fix 为准，后续 API 与部署现状见 `M3-03.md`。

## 目标与实现范围

实现独立面试数据结构和状态服务，为后续 API 做准备；未实现面试 HTTP API、页面、AI 追问、评分或报告生成，未加入题库演示数据。已确认与推荐规则同步到 `M3-01-design.md`。没有引入 V2.5 之外的新依赖。

`InterviewService` 使用 PostgreSQL 面试行锁，在单个短事务内执行状态检查、幂等检查和写入；不调用模型。支持 `pending → in_progress`，达到时间/题数限制且满足规则门槛后进入 `completed`，以及进行中主动终止 `terminated`、异常中断 `interrupted`。三个终态拒绝新的作答和状态变更；同一幂等请求可读取原结果。重复开始不会重置开始时间，重复结束不会改变终态。

主问题和追问分别编号，最多两层追问且追问不增加主问题数；主问题显式关闭后才处理下一个，题数模式最后一题关闭后才检查完成条件。仅练习允许跳题；跳题不计入有效回答。有效主问题数仅统计主问题自身的有效回答；追问回答不计数。有效性采用确定性的文字或数字校验，与模型评价无关。

`InterviewRules` 集中定义已确认规则：2 个不同有效主问题、题数模式至少 3 题、30 分钟无活动、JD 5000 字及确定性有效性校验。调用方必须显式提供规则；创建时保存数值与校验策略标识，后续配置与快照不一致时拒绝操作，防止静默变更。无活动检查采用惰性触发，到期时将场次标记为中断。

时间限制采用 PostgreSQL `clock_timestamp()`，在锁内检查 `now >= deadline`；达门槛则原子完成，未达门槛时进入 `terminated` 并拒绝到期后的出题和作答。题数达限且主问题关闭后，不足门槛同样进入 `terminated`。检查为请求触发，不会在无人访问时自动执行。用户或后续编排可显式终止/中断。

## 数据库结构

新增七张表，未删除、合并原设计表，均独立于普通聊天：

- `interview_presets`：预设类型、名称、版本、启用及配置；`interview_question_bank`：所属预设、题目、知识点、版本及启用状态，按预设建索引。
- `interviews`：状态、模式、预设及配置快照、JD、限制类型与值、开始/截止/最近活动/结束时间、原因、主问题数、有效主问题数和并发版本；状态建索引。检查约束验证状态、模式、限制、计数及时间字段组合。
- `interview_questions`：场次、主问题编号、父题、追问深度、正文及来源快照、关闭时间；场次索引，场次/题号/顺序唯一；复合外键保证父题同场，深度限定 0～2。
- `interview_answers`：场次、题目、回答或跳过、正文、请求标识和提交时间；复合外键保证题目同场，问题唯一、场次/请求标识唯一，检查回答非空和跳题正文为空。
- `interview_reports`：场次、完整/部分类型、独立状态、文字复盘、可空综合分及生成时间；场次索引和类型唯一；数据库禁止部分报告综合分。当前服务仅提供报告占位创建，不接受或生成报告内容、逐题数值或分数，未完成场次不能创建完整报告，无有效回答不能创建部分占位。
- `interview_operations`：场次、操作类型、请求标识、请求体摘要、状态、结果、租约及错误类别；场次/请求标识唯一，重用键且请求不同会拒绝。租约字段为后续工作预留，本轮未实现模型任务调度。

深度递增、父题所属当前主问题、跨表报告状态和正式模式跳题限制由状态服务在场次锁内校验，不能只依赖前端。数据库 CHECK 无法判断自由文字里是否含数字评分；后续报告生成/读取必须采用受约束的文字结构并校验，不能将任意数字评分写入部分报告。

## 遗留问题与 M3-03 依赖

1. 确认的规则保存在版本快照中；未来变更应保留旧策略实现或提供经审批的兼容迁移。
2. 时间或题数达到限制但证据不足时进入 `terminated`；题数模式无活动到期进入 `interrupted`。惰性检查需要读取或写入触发，不是定时任务。
3. 题库尚无经过审核的正式内容；提问题目目前是内部服务输入，未实现 AI 追问或题库 API。题目闭合由后续编排显式调用，必须避免过早关闭当前主问题。
4. 完整/部分报告占位并非生成能力；未完成场次禁止任何数值评分及直接生成学习任务的规则，需在 M3-04 的报告生成和所有 M3-03/后续 API 输出中继续强制。正式模式进行中不得泄露评分评价，也需在 API、SSE 和页面层验收。
5. 数据库表可被绕过服务直接写入，部分跨表约束依赖服务事务；单实例仍无身份认证或公网访问保护。
6. 后续工作仍需解决正式题库来源、HTTP 幂等及错误契约，并继续执行 PostgreSQL 并发测试。

## M3-02-Fix 收尾验收（2026-11-16）

本节为最新结果，覆盖前文中与 R01～R06 冲突的推荐值和待决结论；本轮仅修复 M3-02，未进入 M3-03。

### 六项规则与实现位置

- **R01**：`backend/app/services/interview.py` 的 `valid_submission` 检查 Unicode 字母或数字，排除纯空白、标点、符号、非法控制字符及不合法格式；最大回答长度 12000 字符是本次技术输入上限。`_count_valid_main` 仅统计 `depth=0` 的已提交回答；不会因追问、跳题或技术答案错误改变资格。
- **R02、R04**：`CONFIRMED_RULES` 集中维护题数至少 3、JD 最多 5000 Unicode 字符等值；`create` 服务端校验，只有岗位预设可提交 JD。每场快照保存规则版本 `m302-fix-v1` 和有效性策略 ID；规则不匹配时拒绝操作，旧快照不会被静默改写。
- **R03**：`_expire` 在行锁内用数据库时间检查题数模式 30 分钟无活动；开始及成功提交作答更新活动时间，普通查询和轮询不更新。未过期的运行中操作租约、以及未设置租约的运行中操作阻止误判；后者可能无限阻止超时，需后续执行器负责租约生命周期。时间模式只检查绝对截止时间。检查惰性触发，不保证无人访问时立即更新数据库。
- **R05**：达到时间或主问题流程关闭后的题数上限，主问题有效数至少 2 时 `completed`，否则 `terminated`；写入区分限制和证据不足的 `end_reason`。无活动则 `interrupted`。先取得行锁，再使用服务端时间结算到期/无活动，之后处理当前请求；先取得锁并在期限内提交的答案有效，锁后已到期则不能提交。幂等重试返回已有结果，不重复写入。`add_report_placeholder` 对资格再次检查，不足或无有效回答不伪造报告。
- **R06**：`interview_questions.position` 为同一主问题下的创建顺序，`depth` 为父子层数；`add_question` 在场次行锁中统计全部追问总数，最多 2 条，允许两条并列或链式，追问不增加主问题数。顺序和深度各有限制，数据库唯一约束兜底。

### 风险及结论

六项规则的服务层实现及本轮回归通过，**建议当前数据库环境的 M3-02 通过技术验收**，仍需关注以下限制：旧快照需要明确兼容/迁移方案；生成操作目前仅有租约字段和超时保护，没有模型执行器或租约心跳，后续接入时需以同一行锁维护运行、续约和完成时间，防止操作结束后立即按旧活动时间中断。现有数据库迁移前无 M3 题目，带数据回填已在隔离数据库验证，但其他部署中的旧场次仍需兼容方案。未完成报告的文本内容校验、正式模式 API/SSE 评价隔离和学习任务禁止仍须在后续实现与验收，不能因本轮无相关 API 就宣称已完成。没有开始 M3-03。
